# Search tuning design

No evaluation games have started. Reuse copied srp-public public observation, exact finite deck belief, reconstruction, policy inference, native rollouts, setup and bootstrap. Engine semantics and upstream evidence remain read-only. There are three single-thread nice-10 workers at most for this task, launched through pilot/detach.sh. Existing host jobs are outside this task's ownership.

Initial configuration slate is tuning.configurations(): 14 candidates, covering horizons 160/320/600, intervals 10/20, K 1/2/4, policy top 8/16, script top 4/8, balanced StrategyBot or equal balanced/pressure/defense public-script mixture, tower weight 0/.5, terminal magnitude 2/4. This is a bounded slate, not the full factorial search. Mixture uses the same sampled root for all three styles and averages values. Terminal scores always supersede the added leaf term. The extra tower term is .5 times own minus opponent mean surviving princess HP fraction, with destroyed towers counted as zero. Existing defense-v2 and elixir terms stay intact.

The native API cannot return a rollout endpoint. The tower variant therefore uses the same native transition/action APIs in a short Python loop. Native leaf terminal magnitude 2 is outside its nonterminal range. Terminal4 changes only actual terminal values. Policy continuation variants will be admitted only after timing their required inference cost and establishing a faithful packet conversion; no unvalidated substitute is eligible.

Whole-decision timing includes sensor, history, policy, candidates, reconstruction and rollouts. Warmup runs during Resources initialization and its recurrent state is discarded. Game initialization is separate. The initial screen samples early, middle and late public roots from four fresh-seed script trajectories, never tuning-game outcomes. Probe max above .25 disqualifies. Record all full-game timing; any candidate decision over .25 makes that candidate ineligible for recommendation, even if its score is high. A winner needs a final isolated timing replay; concurrent host work will be disclosed and never stopped without ownership.

Stage 1 gives every timing-eligible candidate 48 games against current. Keep floor(N/2), at least two, ranked by score, then hog26 score, then lexicographic name. Stage 2 gives survivors 96 new games each, keeps the top three or half if smaller, but at least two. Stage 3 gives finalists 192 new games each. Rank using stage-specific outcomes only. A stage must complete before ranking; no outcome-based truncation. A stage with fewer than two eligible survivors cannot establish a tournament winner and stops incomplete. Exact one third Hog26 pairs in every tournament stage. Paired seats preserve world decks and swap controllers. Hog26 H2H uses Hog26 on both sides; holdout uses development/training world decks and swaps controllers. Both planners use the public union of training, development and Hog26 priors because either controller can face either public deck pool.

Common fresh stage seeds across candidates reduce comparison noise. Different stages and confirmation use disjoint seeds. Audit all reports JSON/JSONL seed fields including archived games before any game. Retain failed and interrupted work and never silently count partial pairs.

Confirmation: after selecting the winner, write PREREG.md with winner, source/config/checkpoint hashes, exact schedule, score and bootstrap rules before the first confirmation game. H2H 256 games, 86 Hog26 and 170 holdout. Primary pass requires score >= .55 and matchup-bootstrap lower 95% bound > .50. Secondary scripts: winner/current each 128 holdout and 64 Hog26 on identical seeds and decks, balanced/pressure/defense counts 44/42/42 and 22/22/20. Report pooled and style-specific drops; require no pooled role drop > .05 for recommendation. Bootstrap is copied 10,000 matchup-cluster resamples, RNG 20261001. No extra confirmation attempts or tuning on confirmation outcomes.

Artifacts stay below 1 GiB. No commits or upstream edits. A four-core variant is descriptive only and cannot change the winner or acceptance test; it must respect the three-heavy-process limit and is deferred unless a safe threaded/native implementation is available. No speedup will be inferred from single-core results.
