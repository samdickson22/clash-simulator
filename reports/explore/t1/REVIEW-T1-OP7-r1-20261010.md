## Checks

### 1. Conformance to the authorization

**Confirmed. Nothing is widened.**

- **Root proof** (`apt_budget.py:26-41`): requires UID 0, AND a cgroup exactly equal to `/system.slice/apt-daily.service` or `/system.slice/apt-daily-upgrade.service`, AND an exact command path. The allowed paths are the five DIRECT paths, a system `sh`/`bash` running `/usr/lib/apt/apt.systemd.daily`, or a system `python`/`python3` running `unattended-upgrade` or `apt-check`.
- **Descendant proof** (`apt_budget.py:54-69`): every hop up the observed parent chain must keep the same cgroup and UID 0, up to a root that passes the root proof. The walk is capped at 64 hops and is cycle-safe.
- **No other units, no non-root processes, no name-only matching.**
- **Name-only processes still stop.** I checked by test and by probe:
  - A process named `unattended-upgrade` with the wrong cgroup, no cgroup, or a non-root UID stays foreign (`test_op7.py:57-68`).
  - A non-Python `apt-get`/`dpkg` in the wrong cgroup stops (`test_op7.py:70-73`).
  - An orphaned Python process inside the apt cgroup with no observed root also stops (probe e).
- **The new `apt_command` rule** (`host_audit.py:90-91`) makes unproven apt-named commands foreign even when they're not Python. That is stricter than the base, which never stopped root non-Python processes. It fails closed, so it's acceptable. Note that root `dpkg`/`apt-get` run outside these two units, for example by a sysadmin or packagekit, will now stop. That matches "any other foreign process still stops".
- **Live layout on 05** (same image as 01/08):

### 2. Spoofing and edge cases

- **PID reuse.** Meters key on (pid, start_ticks). The cgroup is read between the first stat read and the recheck of start_ticks, ppid and UID (`host_audit.py:42-61`), so a reused PID is dropped. One window remains: the process exits between the cgroup read and the recheck, which keeps the row through the `FileNotFoundError` path. Exploiting it would need PID reuse within microseconds (pid_max is 4194304) by a UID-0 process already inside the apt cgroup. Negligible.
- **Cgroup v1 vs v2.**
  - Ubuntu 20.04 is hybrid, with both `1:name=systemd:` and `0::` lines. I verified live on 05 that `capture_cgroup` returns `/system.slice/cron.service` for cron, `/init.scope` for PID 1 and the session scope for self.
  - Pure v2 and pure v1 with name=systemd both parse.
  - Conflicting lines return None and fail closed.
  - Missing in tests: a full multi-line hybrid fixture (F9).
- **Who can enter the cgroup.** Only root can place a process in `system.slice/apt-daily*.service`. The cgroup is the real trust anchor. The UID comes from the owner of the `/proc/<pid>` directory, which is weaker (F5).
- **dpkg maintainer scripts running arbitrary binaries.** These are budgeted, as "their children" requires. Probe (d): `gcc` under `dpkg` inside the upgrade unit is budgeted. This is acceptable, because the caps bound it:
  - a DKMS rebuild (NVIDIA 470 on a kernel security update) runs `make -j$(nproc)`, which exceeds 150% in one sample and stops;
  - a single-threaded compile or initramfs compression of more than about 10% of block wall time stops on the average cap.
  - Every child command is recorded in `ubuntu-apt-occurrences.jsonl` and in the proof.

### 3. Meter correctness

- **Double counting of cutime/cstime: confirmed, and worse than documented.** See F1. With a budgeted chain of depth d, each observed descendant's CPU is charged once live and once more at each reaping on the way up. Probe (b): a 4-deep chain using 100 real ticks was metered at **400**. The reaped lifetime total also lands in a single census sample.
- **The 60 s minimum.** The average is cumulative from block start, so a burst in the first 60 s is still caught at the first census after 60 s. Blocks shorter than 60 s get only the sample cap.
  - A block that crosses 10% between its last census and completion finishes as flagged only. Its proof records `stop=True`, but nothing acts on it. OP-6 has the same gap (F10).
- **apt and ssh at the same time: separate budgets.** The combined worst case without a stop is about 22% of a core averaged over a block (10% SSH + 2% idle + 10% apt) and about 325% in one sample.
  - A combined cap is **not required for timing validity**. Both meters flag at 0.5%, every flagged block is disclosed, and the primary analysis is pre-registered to include all blocks.
  - Co-occurrence of the two is rare, since apt runs a few minutes a day.
  - Cheap pre-outcome fix: add a union exclusion (ssh OR apt) to the descriptive analysis and report co-flag counts (F3).

## Findings

1. **F1 — HIGH (efficacy, not validity). Reaped child lifetime CPU is charged in one sample and again at every level of the tree.**
   - **Where:** `apt_budget.py:84-91` (`sample`) and `apt_budget.py:99-106` (`update`), through `ssh_budget.increment`/`total_ticks` (`ssh_budget.py:72-75`). The documentation understates it at `OP7-T1.md:34-36`.
   - **Mechanism:** a budgeted parent's self+cutime delta jumps by the child's whole lifetime CPU, including its own reaped subtree, in the census where the child is reaped. That CPU was already metered live.
   - **Consequences:**
     - The sample cap fires whenever any budgeted child with lifetime CPU above about 1.5×dt is reaped. dt is about 1.3–1.6 s (a 1 s sleep plus the census), so the threshold is about 2 s. That's a likely range for `apt-get update` and `unattended-upgrade --download-only`. 05's last apt-daily run took 18 s wall.
     - The block average is over-counted by about the tree depth: 4× in probe (b). That makes average stops and flags more likely too.
     - The worker's own `test_average_floor_and_reaped_children` treats the lump as intended.
   - **Fix:** for each budgeted row, charge the self-tick delta, plus the cutime delta minus the last-observed totals of budgeted children of that row that disappeared this interval, clamped at 0. Add tests:
     - reaping a 5 s observed child doesn't trip the sample cap;
     - nested reaping charges each tick once;
     - CPU of an unobserved short-lived child is still charged.
   - **Note:** OP-6 shares this design; whether to back-port the fix is the coordinator's call. 08's live bytes must stay unchanged.

2. **F2 — MEDIUM (a gap in the authorization, not a defect in the diff). apt's sandboxed `_apt` children (UID 105) will still stop the host.**
   - **What:** apt runs its acquire methods (http/https/store/rred/gpgv) as `_apt`. On 05, `APT::Sandbox::User "_apt"` and `_apt` is UID 105.
   - **Effect:** those processes are correctly unbudgeted, since the authorization says UID 0. But they're non-root and not allowlisted, so any of them using more than 0.1 s of CPU between two censuses is `foreign_active` (`host_audit.py:186-191`) and stops the host. rred applying pdiffs and xz decompression make that plausible during `apt-get update`.
   - **Also:** their CPU is later charged into `apt-get`'s cutime, which feeds F1.
   - **Asks:**
     - The worker must not widen scope on their own.
     - The coordinator should decide whether to extend OP-7 to UID-105 `_apt` descendants with the same cgroup and an observed UID-0 root generation, under the same shared meter.
     - OP7-T1.md should disclose this residual either way.

3. **F3 — LOW. The SSH and apt budgets don't share a cap, and no sensitivity row excludes blocks flagged by either.**
   - **Where:** `reduce.py:135-138`; RELEASE-PRODUCTION-CHECKS PC4.
   - **Assessment:** not needed for validity (see check 3). Recommended while still pre-outcome:
     - add a third descriptive analysis excluding blocks flagged by SSH OR apt;
     - have PC4 report both-flag counts by cell/population.

4. **F4 — LOW. `apt_command` fails open when `shlex` can't parse the command.**
   - **Where:** `apt_budget.py:43-52`.
   - **Effect:** an apt lookalike with an unbalanced quote, for example `/tmp/apt-get 'x`, returns False and falls back to the base rules, so a non-Python lookalike isn't forbidden (probe c). This is not a regression from the base.
   - **Fix:** fall back to `cmd.split()` for the name test.

5. **F5 — LOW. The UID evidence is the owner of the `/proc/<pid>` directory** (`host_audit.py:42`).
   - **Problem:** non-dumpable processes (setuid/setcap binaries, ssh-agent, `prctl(PR_SET_DUMPABLE,0)`) show up as owned by root.
   - **Impact for OP-7:** limited, because the cgroup anchor needs root. I found no such process on 05 right now.
   - **Fix:** read the real and effective UID from `/proc/<pid>/status` for the OP-7 proof.
   - **Out of scope, but worth knowing:** the same weakness lets a non-dumpable user process escape the base `foreign_active` check, which is restricted to non-root processes.

6. **F6 — LOW. `analyze` is slightly less strict than before** (`ssh_sensitivity.py:58-60`).

   - **Fix:** keep `entry[flag_key]` strict, since both keys are always written.
