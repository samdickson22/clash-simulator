11. **MAJOR — A drainage syscall failure is still treated as an ordinary block/listing error, so copying continues with an undrained transport.** `oa1/mirror_k4s.py:97–114,130–132,330–347,384–385`.

   Scenario: a transport times out or its leader completes, and finish() attempts to terminate/prove the owned group gone. os.killpg() raises an OSError other than ProcessLookupError, for example PermissionError/EPERM. drain() catches only ProcessLookupError; only expiration of its polling loop becomes LifecycleError. An unexpected error enumerating /proc likewise escapes as an OSError. finish() retains the PENDING entry but propagates the original error after its bounded p.wait(). Since OSError is in ERRORS, one_pass() records an ordinary listing/block error and may immediately start more transports. The main LifecycleError handler is never entered. This violates the coordinator's explicit requirement that a drain failure be LifecycleError with exit 3, and repeats the failure-propagation part of finding 6.

   **Independent evidence on /bin/python3 3.8.10:** I ran actual M.run() under an anonymous-memfd exclusive flock, injecting PermissionError only for killpg calls targeting its first reviewer-created group. The group was a bash holder running sleep 30. After its 0.1-second call deadline and finish()'s five-second reap wait, the exception was PermissionError, isinstance(error, ERRORS) was true, PENDING retained PGID 783899, and both holder/sleep were still live. I then exercised actual one_pass() with two synthetic block IDs, replacing only scientific copy/ACK/file operations. The first copy called actual run(['sleep','30'], .1); the second called actual run(['true'], .1). The first group's killpg calls again raised synthetic EPERM; signals to the second reviewer-created group used the real syscall. one_pass() started and completed the second transport while the first group remained alive:

   - first PGID 900131, live members [900131, 900138], returncode None;
   - second PGID 909791, returncode 0;
   - block_errors = {'smoke-0001': 'PermissionError: synthetic kernel killpg EPERM'};
   - lifecycle_error = null; PENDING = {900131}.

   This is fault injection, not evidence that the healthy hub currently denies signals. It proves the error path and continued transport launch using real local process groups. All surviving reviewer-created groups were explicitly drained and reaped afterward. No SSH, game file, filesystem exhaustion, or external process was involved.

   The new read-only own_transports_gone() correctly refused the still-live group with AssertionError. Thus this control does **not** demonstrate successful revocation while that tracked group remains live. The defect is that fail-stop occurs only at eventual teardown, if the group is still alive then; a long-running copier can continue passes indefinitely, and a group that exits naturally before teardown no longer forces exit 3. A health record with lifecycle_error=null does not report this lifecycle failure honestly.

   **Fix:** convert failures from owned-group drainage/reaping into LifecycleError at the lifecycle boundary, preserving their original cause and retaining unresolved PENDING state. Only a positively completed drain/reap should retire the entry. Preserve the existing re-raise behavior for an original transfer error after successful cleanup. Do not add recovery signals, fd-holder scans, or ledger-based kills. Add fault controls for killpg OSError and failed group enumeration through actual run()/one_pass()/main(), asserting no next block transport, lifecycle health and exit 3, and refusal of revocation while a pending group lives. The current test monkeypatches drain() to raise LifecycleError itself, so it assumes rather than verifies this conversion.
