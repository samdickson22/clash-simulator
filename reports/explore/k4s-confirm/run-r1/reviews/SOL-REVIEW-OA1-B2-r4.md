9. **MAJOR — Recovery can kill unrelated processes: ledger PGIDs are not generation-checked, and an open lock-file fd is not proof of transport ownership.** `oa1/mirror_k4s.py:149–178`.

   Failure scenario A: a root dies after writing a `start` record and before a `done` record. Its transport later exits naturally, or explicit recovery drains it. Recovery does not append a completion record, so that stale start can remain indefinitely. Linux subsequently reuses its numeric PID/PGID for an unrelated process group. `orphan_transports()` selects any current group with that PGID, without comparing the recorded `start_ticks`, `root`, or command. `recover_transports()` unions that ledger selection with the fd scan and signals the whole group. The same-UID/job-lock-fd restriction applies only to the fd-scan arm of this union; a ledger-selected group need not have any job-lock fd at all. This can terminate another job or user session on the hub. A recycled group can also spuriously prevent registration.

   Independent evidence on `/bin/python3` 3.8.10: I created a harmless separate-session `sleep 60` group and supplied the actual ledger reader with an in-memory stale `start` record using that PGID but a deliberately different start time. `lock_holders()` returned `[]`. The actual `orphan_transports()` still selected the record, and the actual `recover_transports()` drained the unrelated group; its return code was `-15`. Representative output was `recorded_start=153575788`, `live_start=153575789`, selected/drained PGID `3450513`, and no lock holders. This emulates PID reuse directly without waiting for the kernel to cycle PIDs. All signals were restricted to reviewer-created harmless groups.

   Failure scenario B: a same-UID diagnostic or lock contender independently opens the job's lock file, without inheriting the copier's open file description or acquiring its flock. `lock_holders()` identifies every matching open fd, not owners of the inherited flock. Apart from the command-string substring refusal for `mirror_k4s.py`, recovery kills every such process's entire group. That group may contain unrelated peers; it need not be a transport group or even have a dead copier ancestor. Excluding only the review/recovery PID also does not exclude its group if another member opens the file.

   Independent evidence: with an anonymous memfd representing the lock inode, the reviewer held an exclusive flock and a separate-session Python process independently opened `/proc/<reviewer>/fd/<lockfd>` read-only, then slept. It had no inherited lock fd and had acquired no flock. The actual fd scan selected it, and actual recovery killed it with return code `-15`. The same inode/open-file-description distinction applies to the regular job lock. This is a second ownership defect, independent of ledger PGID reuse.

   Fix: validate a ledger transport's generation before signaling; the existing `start_ticks` must not be ignored. A mismatched or ambiguous generation must never authorize `killpg`. Retire confirmed completed/recovered generations so stale starts do not remain candidates. Bind unledgered recovery to an identifiable OA-1 holder in its own transport session and the correct lock inode/custody, rechecking identities immediately before signaling. A same-UID process merely opening the file is insufficient authorization; refuse recovery on an unverified holder instead of killing it or its group. Protect the current/root group explicitly. Preserve support for a finished leader with surviving genuine helpers using verified identities/custody rather than reverting to bare numeric PGID selection. Add negative controls for a reused PGID, an independent unflocked opener, and a nontransport/current group; all must survive recovery without being signaled.

10. **MAJOR — The initial ledger append/fsync is outside the cleanup guard; its failure leaves a transport alive and is downgraded to a block/listing error.** `oa1/mirror_k4s.py:105–106,119–126,235–240,347–361,393–410`.

   Failure scenario: `Popen` succeeds and starts an SSH/rsync holder, then opening/writing/flushing/fsyncing the start ledger fails, for example because the job filesystem is full or returns an I/O error. Line 121 executes before the `try` at line 122, so neither `drain()` nor `wait()` executes. The live operation may already be able to publish remotely. The resulting `OSError` is included in `ERRORS`; `one_pass()` records it as an ordinary listing/block error and can start subsequent transports. The original `Popen` is no longer retained by the application for cleanup.

   In normal teardown, `revoke(j, host, me)` skips `recover_transports()`; only recovery with `me=None` calls it. Thus source quiescence and inactive-receipt comparisons can run while an old local operation remains capable of subsequently initiating remote work. `--once` can return 0 if those comparisons happen to succeed. If the inherited lock still has a holder, it prevents a successor but does not prevent the current root from continuing work or claiming successful revocation. `rsync --timeout=120` is an inactivity limit, not proof that the operation is already gone when revocation is claimed.

   Independent evidence on Python 3.8: I held a real flock on an anonymous memfd, invoked the actual `M.run(['sleep','60'],300)`, and made the first `ledger()` call raise `OSError('synthetic ENOSPC start append')`. After the exception, the holder and sleep remained live and both held the fd; representative PGID `3451219` had members `[3451219,3451227]`. I then exercised the actual `one_pass()` listing boundary with the same failure: it returned `error='listing OSError: synthetic ENOSPC'`, `lifecycle_error=None`, while members `[3664840,3664849]` remained alive. Every spawned group was explicitly drained/reaped by the reviewer afterward. No filesystem exhaustion or study file mutation was used.

   Fix: place all work after successful `Popen`, including the start append/fsync, inside an unconditional cleanup/reap guard. A lifecycle-accounting failure must stop further transports and surface as `LifecycleError` with exit 3 unless cleanup and the required accounting are proved safe; it must not reach the retryable block/listing handlers with a live group. Keep pending process identities available for teardown until drain is verified. Before successful normal revocation, prove all prior local transport groups are gone; do not restrict that check to `me=None`. Add separate start-open/write/flush/fsync failure controls asserting no survivor, no subsequent block transport, and honest lifecycle status. Exercise actual failed drainage in teardown, rather than only injecting `LifecycleError` from listing/return-ACK.

   Related crash-record limitation: `ledger()` does flush and fsync completed appends, but recovery parses every line with unconditional `json.loads()`. A partial final record after an interrupted/short/erroring write raises before fd-holder recovery can proceed. Handle an incomplete trailing record conservatively, using verified holder recovery and an explicit accounting error. Do not treat a corrupt ledger as empty or use it to authorize an unverified PGID. This is a recovery-liveness limitation in the same accounting path, not evidence of successful unsafe revocation by itself.
