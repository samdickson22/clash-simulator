## Findings

1. **MAJOR — Failed qualification/runtime comparison can be followed by smoke carry-over and a successful finalize. Lines 99–107.**

   The SSH shell does not inherit the local `set -euo pipefail`. The Python heredoc checks runtime-pin equality and qualification PASS, but its exit status is discarded: the next command starts with `test ! -e ... && cp ... && test ...`. On a fresh destination, successful copying and manifest hashing make SSH return zero even after an assertion, parse error or missing smoke runtime pin. Finalize then copies the dispatch, constructs authorization and runs the barrier. The frozen barrier checks manifest files and freeze authority, not this fresh qualification or equivalence to the smoke runtime; `supervise.py:35–40` requires qualification markers and verifies the destination's own pin, rather than enforcing this comparison. Thus those later checks do not substitute for the failed check.

   **Fix:** run the remote body under explicit strict shell options, and explicitly make successful completion of the Python check a prerequisite for carry-over. Check the qualification's host, job and current runtime-pin hash as well as PASS/checks. Verify the current runtime bytes against the pin and verify copied smoke-admission/SMOKE-PASS bindings against the preserved authorization. Do not publish a successful finalize receipt until both hosts pass. A local, synthetic shell control reproduced a failed Python assertion followed by successful carry-over-shaped commands and exit zero; no actual carry-over was performed.

2. **MAJOR — Stop/drain do not prove the claimed quiescence and can mask failed metadata checks. Lines 28, 33–45, 51–54.**

   Stop waits on a PID extracted by unchecked grep pipelines, then prints the supervisor receipt and an `owned_groups` count. The count is never asserted to be zero. A failed Python receipt read can be hidden by the final successful `echo`, and failures in the process-listing pipeline can also produce an apparently valid count. Matching command lines containing the job path is not an inventory of all members of the recorded worker groups: descendants need not contain that path. PID existence alone does not identify the pinned supervisor or distinguish a zombie/reused PID.

   Drain's remote `find ... | wc -l` has no remote pipefail. A failed find can return count zero with SSH status zero. A stale health receipt with zero counters can then satisfy the initial ACK check. The final check establishes `revoked`/inactive/no lifecycle error but does not re-establish the complete ACK set, freshness, host/phase or copier identity. The source check greps only for `active: false`, without matching the admission identity. Removing STOP-COPY before those final checks also loses the stop request on a failed verification. Inventory subsequently requires only a nonempty supervisor-exit file; it has no verified stop/drain receipt prerequisite.

   **Fix:** explicitly fail on every remote parse/process/find error. Bind launch, exit and ownership receipts to the requested host/job/phase/dispatch. Read the supervisor admission's full identity and worker-group inventory; prove the original supervisor and every recorded worker group have no live members without signaling other processes. Match the complete block-ID set against the supervisor's completed descriptors, returned ACK markers and final copier health; bind health and both admission receipts to the same copier identity and phase. Require final revocation/quiescence before removing the owned STOP-COPY token. Persist the two-host stop/drain proof and require it before inventory. A synthetic failed-find pipeline returned zero/count zero in the local control.

3. **MAJOR — Historical hub membership and counted-block provenance are not bound to this run. Lines 57–83; input construction at 51–63.**

   The hub glob searches **every** `k4s-confirm-*` namespace under both roots, not just this run's authenticated reporting namespace and preceding replacement namespaces. Existence of hub-ack.json is its only admission test. Duplicate durable IDs are correctly rejected, but an unrelated namespace with a distinct ID can supply a missing logical block. Frozen `replace.py:27–31` checks a selected block's seed, game counts and raw hashes; it does not compare the complete canonical descriptor, runtime binding, ACK contents, physical source host or namespace against the expected dispatch. An unrelated run using the same seed/count can therefore be substituted. For historical blocks outside the newly inventoried phases, this invocation does not perform even those integrity checks.

   The coverage assertion is useful arithmetic, but counted descriptors are not passed through `canonical()` and their IDs are not matched to authenticated historical dispatch rows. It counts `descriptor.replaces or descriptor.id` and ignores ACK job/phase/host/proof bindings. A same-ID completion from the wrong runtime/namespace can pass exact coverage. Conversely, unrelated extra blocks or duplicates can stop a legitimate inventory. A cumulative view across legitimate namespaces is necessary because never-started IDs migrate unchanged; descriptor IDs are not unique across dispatch phases, although acknowledged durable IDs should occur only once.

   **Fix:** construct a recorded allowlist of this run's historical `(host, job, phase, dispatch SHA)` bindings, and build the hub view only from those locations. Validate ACK bindings and complete descriptors against the appropriate historical dispatch, canonical schedule and frozen runtime provenance before counting them. Preserve the duplicate-ID and exact logical coverage checks. Require source metadata for the current stopped remainder on both hosts, validate its host/phase/dispatch bindings, and reject duplicate or stale source selections. Supply **all historical dispatches** for host-assignment history, but do not indiscriminately supply every historical phase as a source: reissued never-started IDs across sources trigger frozen `replace.py`'s `seen` assertion. These are different input roles.

4. **MAJOR — A failed inventory leaves an authoritative dispatch and a partially advanced cumulative ledger. Lines 49, 52, 58, 63–85, 95, 117–127.**

   Frozen `replace.py:46–55` writes the live ledger after each loss and writes the dispatch before round.sh runs coverage. A cap/bank failure can leave some seeds consumed with no dispatch; a coverage failure leaves the final-named dispatch present. The hub-view directory is also created before success and prevents a same-number retry. Re-running inventory with the advanced ledger skips already recorded lost IDs (`replace.py:48`) and does not regenerate their replacement rows. This can strand assignments even though later coverage detects the omission. Finalize and launch do not require proof that coverage succeeded; the existence of the dispatch suffices, and the frozen reporting barrier does not check coverage or dispatch/ledger agreement.

   **Fix:** hold a round/ledger lock, preserve an immutable input-ledger snapshot, and invoke the unchanged frozen tool once against a working ledger and unpublished dispatch. Check descriptors, authenticated cumulative coverage and ledger/dispatch agreement before publishing a hash-bound successful inventory receipt. Promote the verified artifacts through an explicit recoverable publication step; finalize/launch must require that receipt and its exact hashes. Retain failed artifacts as diagnostics and stop for reconciliation rather than retrying against an already advanced authoritative ledger. Do not patch the frozen replacement algorithm.

5. **MAJOR — P2's required prelaunch conditions and escalation gates are omitted. Lines 80–85, 86–127.**

   Option A at `COORDINATOR.md` commit `afe83faa` retains timer readings and motd pre-trigger checks before every launch, and requires escalation at 150 primary or 45 guard losses, near cell-bank exhaustion, or an unexpected non-apt/motd stop. Standing policy P2 at `adc12f36` requires relaunch after the timer fires, maintenance exits and stale motd stamps are pre-triggered. For r2 it also provides the coordinator-controlled 03 builder window, including its 30-minute fallback. The script prints ledger counts/max k but enforces none of those prerequisites. Ordinary frozen admission can allow source-proven apt work within its budgets; it does not prove maintenance has exited or prevent a later motd check. Consequently `launch N` can run too early or beyond the standing authorization's escalation conditions.

   **Fix:** make these mandatory prelaunch checks, or require a fresh, hash-bound manual/coordinator prelaunch receipt proving them. Check the applicable timer occurrence and maintenance exit, both stamps, escalation disposition and any current 03 read-window disposition immediately before launch. Keep the hand-driven scheduling model if desired; document these required steps in the command sequence and make missing evidence fail closed. The r1 launch receipt contains timer/stamp evidence, so this omission is not evidence that r1 skipped them.

6. **MINOR — First inventory cannot enumerate an empty replacement history. Line 62.**

   With no existing replacement-r*.json, `ls` exits nonzero even though stderr is suppressed. An assignment containing that command substitution returns its failure status, so local `set -e` exits before replace.py. The newly created hub-view directory remains and blocks a straightforward retry. A synthetic `set -e; a=(fixed $(false))` control exited 1 before its next statement.

   **Fix:** use shell glob arrays with nullglob and explicitly retain reporting-dispatch.json, without `ls` or word splitting. Validate the expected numeric prior-round history and required launch-dispatch hashes. There are already r1 history files in the supplied workspace, so this is a bootstrap defect rather than an observed r2 failure.

7. **MINOR — The staged-extras interface is not satisfied by the available stage helper. Lines 90–92; `/mpac/sdicks02/k4s-runner/stage/stage_host.sh:10`.**

   Round exports a new namespace-specific tar and passes `EXTRAS_TAR=.../extras-repl-rN.tar`, but the available local stage_host.sh unconditionally extracts `$S/extras.tar` and never reads EXTRAS_TAR. That older archive can contain T1-reference plan paths rebound to an earlier job rather than the fresh namespace. Frozen source-binding checks should reject the mismatch, preventing qualification completion, but the advertised fresh qualification workflow then stalls. I did not inspect the host copies, so I cannot assert that they share this mismatch; their bytes are also not bound by round.sh.

   **Fix:** verify/bind the actual operational stage helper's bytes and interface before using it. Have the non-frozen helper consume the explicitly selected archive, or extract that verified archive explicitly into the fresh job in round.sh. Confirm the rebound reference paths and archive SHA. Do not infer the remote helper's interface from an environment assignment or change frozen stage_k4s.py.

8. **MINOR — Launch reports detachment, not successful supervisor admission on both hosts. Lines 125–127; `tools/launch_phase.sh:37`; frozen `launch.sh:21`, `detach.sh:9–14`.**

   The helper verifies copier registration and calls the frozen launcher, which returns once the detached PID receipt exists. The supervisor can subsequently fail admission, barrier or runtime verification before writing launch.json. Round can therefore return zero or start the other host without detecting that failure. The two successful r1 launch/admission receipts demonstrate that this did not occur in the supplied r1 evidence.

   **Fix:** after detachment, wait with a bound for the correctly identified supervisor's admission and launch receipts, verify their dispatch/runtime/phase bindings, and detect early exit. Report a two-host launch as successful only after both are confirmed. If one fails, retain evidence and use the authorized owned-stop/reconciliation procedure for the other host.
