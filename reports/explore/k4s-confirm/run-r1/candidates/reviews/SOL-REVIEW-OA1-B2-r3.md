## Retained MAJOR and new finding

6. **MAJOR — SIGKILL recovery does not account for surviving local transport groups; remote pgrep is not a lifetime barrier.** `oa1/mirror_k4s.py:99–107,142–157,159–170,173–196,319–322,346–347`.

   Scenario: the copier root dies while `run()` has an rsync/ssh operation in flight. Each operation has `start_new_session=True`; the lock descriptor is not passed to it. SIGKILL runs no `finally` or `drain()`. Consequently, the old local group survives independently while the root's job lock becomes available. A new invocation checks only the recorded root generation and source-side processes already matching `^rsync --server .* <job>/`. A surviving local transport that has not yet reached remote rsync execution, or a remote shell before it execs rsync, is absent from that check. The source can be momentarily empty while the previous operation remains able to start work later. Neither registration nor explicit `--revoke` enumerates or drains old local groups, and the old root's 30/300-second Python timeout enforcement died with the root. Two receipt snapshots five seconds apart do not prove those operations can no longer run.

   This is a remaining part of round 2 finding 6, rather than a new demand that SIGKILL execute cleanup. The documented `--revoke` recovery is supposed to establish a safe hand-off after such an interruption; it currently lacks the necessary local transport accounting. Late block/ACK activity and overlap with a successor remain possible. Source-side quiescence improves already-running remote receiver handling but does not establish that no prior producer can subsequently create one.

   **Independent evidence:** on `/bin/python3` 3.8.10, a child reviewer process called the actual `M.run(['sleep','60'],300)`. The transport had its own PGID. Killing only its root with SIGKILL left a live, non-zombie transport group. A second control used the same exclusive nonblocking flock semantics on an in-memory lock inode: the root held the lock before SIGKILL; the reviewer acquired that same inode's lock afterward while the old actual-`run()` transport remained alive. Both surviving groups were explicitly drained by the reviewer. These controls involved no network, game files, or persistent fixture files. The independent source-pattern control also rejects a pre-exec `bash -c ... rsync --server ... <job>/...` title.

   There is a related failure-propagation edge: `drain()` can explicitly fail while a non-zombie group remains (`89–97`), but `one_pass()` catches that `RuntimeError` as an ordinary listing/block error (`289–303`) and may continue starting transports. There is no retained group record for later cleanup. Revocation can then run and release the lock without proving that failed local drain has subsequently succeeded. A transport-lifecycle failure must not be reduced to a recoverable block error.

   **Fix:** account for transport groups independently of root liveness and prevent a successor or successful revocation while an old local group can still operate. For example, retain generation-bound transport identities using a crash-safe mechanism before transport work can begin, and have both registration and `--revoke` drain/confirm those groups under the job lock before remote quiescence and receipt publication. A lock inherited and retained through the complete transport lifetime is another possible part of the design, but must cover helpers as well as the direct leader and still handle remote receivers. Treat failed local drain as a lifecycle failure, with explicit unresolved status and recovery, rather than continuing the pass. Add a local root-SIGKILL/recovery regression with a delayed harmless transport, proving that no old local operation overlaps a successor or confirmed recovery, and a drain-failure propagation control. Do not change the frozen guard.

8. **MINOR — Quarantine re-copy can repeatedly skip the corrupt bytes it is intended to repair.** `oa1/mirror_k4s.py:52,225–229,239–246`.

   Scenario: a retained hub game suffers corruption that preserves its size and modification time, as with bit rot or restoration of corrupt data with preserved metadata. Startup detects the SHA mismatch and quarantines ACK/marker/proof, but leaves the game files in place. The subsequent raw pull uses `rsync -a` without `--checksum` or `--ignore-times`. Rsync's default size/modification-time quick check can skip the damaged game. Hash verification then fails again on every attempt, although the source remains correct. No bad ACK is returned, but automatic repair stalls. The supplied re-copy test mocks rsync by unconditionally overwriting files and therefore cannot expose this behavior. Local `rsync --help` explicitly documents these skip criteria and the overriding options.

   **Small precise fix:** add `--ignore-times` to the raw block pull at line 242, or otherwise force transfer of quarantined games before re-verification. Add a synthetic repair control with different same-length source/hub bytes and identical mtimes, exercising actual local rsync behavior. This is a recovery/liveness defect, not an unsafe ACK publication.

## Lifecycle, pattern, verification cost, and sealing

`run()` correctly places ordinary rsync and its SSH helper in a separate group, uses `/dev/null` for stdin, and uses a temporary file for stderr. `communicate(timeout=...)` remains bounded even if an inherited stdout pipe stays open. Normal completion drains helpers left after leader exit; timeout/error drains before re-raising. `group_members()` parses the correct `/proc/stat` process-group field and excludes zombies. Zombies cannot execute transport or hold open descriptors, so excluding them is appropriate; the direct child is reaped by communicate/wait. A process-group scan is not a general detector of a descendant that deliberately creates another session, but the ordinary rsync/ssh process model does not require such a descendant.

The requested suite ran on the freeze virtualenv's Python 3.12.12: **35 passed in 2.37 seconds**. I separately parsed both scripts and exercised the actual `run()`/`drain()` on `/bin/python3` **3.8.10**: timeout with a grandchild, failed leader with a helper, successful leader with a helper, and SIGTERM during a real transport all passed. The surviving-group controls above also used 3.8. No Python 3.8 syntax/API incompatibility was found.

Signal handlers are installed before lock acquisition and only append a stop request. The current bounded block operation finishes; the pass stops between blocks; revocation completes before the lock is closed. That avoids the earlier signal-induced subprocess unwinding. The STOP-COPY/signal check is not inside startup hashing or every constituent transfer, so stop latency includes the current block operation or remaining startup verification. `--revoke` now shares the lock and deferred signal handling; an exception in that branch exits nonzero, although it does not produce the normal branch's fresh `lifecycle_error` health receipt.

For the exact emitted command forms, the remote pgrep pattern matches sender and receiver rsync processes for both block paths and the admission receipt. Its final `<job>/` boundary **does not match** `/mpac/sdicks02/jobs/clasher/k4s-confirm-r1-stopdrill/` when checking `k4s-confirm-r1/`; I verified that explicitly. The permitted roots/job names contain no regex metacharacters needing escape. The leading `^rsync --server` avoids matching the pgrep command itself or an unrelated shell merely containing the text. An unrelated rsync server actually accessing the same job is conservatively included, appropriately blocking hand-off. False negatives include pre-exec wrappers, local operations before remote execution, and a server invoked with `/usr/bin/rsync` as argv[0]. The latter is not the script's present emitted `rsync` argv form; the pre-exec/local gaps matter to finding 6. No cross-job prefix false positive was found.

Startup verification hashes all retained games of the selected phase once and quarantines invalid blocks without sending their ACKs. Its cost is proportional to total retained game bytes; it uses `read_bytes()` one game at a time. It does not parse game contents. Healthy returned blocks are not fully rehashed every ten-second pass: the lifetime `verified` set avoids that, while the returned marker checks ACK/proof hashes. A fresh block is hashed once during copying and again before its ACK is returned. This relies on the intended immutable, owned hub tree during a copier lifetime; arbitrary concurrent mutation is not excluded by the job flock. No cost benchmark read real game data. Complete startup verification before depending on the copier for a reporting supervisor's 30-minute ACK deadline.

Quarantine removes active hub ACK/returned/proof names and records the integrity error; re-copy retries against the original source and checks every game before rebuilding an ACK. Other blocks continue. Existing source ACKs are not retracted by quarantine; hub health correctly stops counting the quarantined block. This is an opaque-byte repair mechanism and does not rewrite or interpret scientific records. MINOR 8 limits its present automatic repair behavior.

`tools/k4s_health.py` is outcome-blind under the frozen producer's owned regular-file layout. Its fixed remote job paths and validated phase restrict its reads to operational metadata: progress, launch, stop/supervisor-exit reason, admission-active status, exit-complete flags, and complete-proof interference flags. Frozen `run.py:377–378` creates the proof from descriptor, identity, timing and game SHAs; `supervise.py:89,93,109,119` adds interference and writes the operational records. This is not a hostile-symlink sandbox or a proof about arbitrary substituted metadata files.
