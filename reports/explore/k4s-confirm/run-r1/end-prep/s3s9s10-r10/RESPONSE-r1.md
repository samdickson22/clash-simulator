## Deviations and decisions to confirm (disclosed, not hidden)

1. **D1 member set + 6 support files.** The frozen verifiers read six tracked files that are outside (runtime-pin-r2 ∪ `*.py`) at origin/main: `runtime-pin-r2.json`, `qualified-source-binding.json`, `K4S-MAC-MANIFEST.json`, `K4S-MAC-PROCEDURE.md`, `e4v3/spec-pins.json`, `e4v3/build_tiers.sh`. This was checked from tree metadata, with the pin list read pinned. Without them `prepare_bundle.runtime_pins(root)` cannot even open its own pin list, and `measurement_files` cannot reach 42b8986d. S9 adds exactly these six (`SUPPORT_MEMBERS`, s9:68–74). Each is pinned (f81f3655 / 56b67dd4 / 74314eda / K4S manifest / measurement inventory), and none enters `runtime_files`. **Coordinator: please confirm this reading of D1.**
2. **One git call outside `git_run`.** The `prepare-clone` network clone is the only one; the reason is in the S9 table. Everything after it goes through safe_input, and the clone is verified before any read.
3. **S3 removes one file.** It unlinks its own freshly fetched `FETCH_HEAD` inside its own `.partial`, via `unlink_own`: gated, single-link, regular. Git 2.25 has no `--no-write-fetch-head`. No other local delete exists apart from S3's throw-away tempdir.
4. **Guard repo refs** are written as loose ref files, because `update-ref` and `config` are not in `si.GIT_SUBCOMMANDS`. There is no `gc.auto=0`: the r1 config key cannot be set without `git config`. The guard repo is never gc'd by the frozen reads.
5. **Receipt-based on-host verification.** The receiver hashes the streamed bytes while writing, fsyncs, and reports size, SHA, nlink and mode per file. S10 no longer re-reads every staged file from disk on the host as r1's TV did: the reader is capped at 256 items, and the runtime has more than 4,000 files. After F, POST proves the directory identity (dev/ino) and the modes.
6. **Reads of own outputs without an expected SHA.** The guard repo's `.git/config` and the full clone's `.git/config` are read and their keys allowlisted. Their content is produced by git in this run, so it has no prior SHA. Freshly copied S1b files are re-hashed and compared. Externals are hashed at their exact Q5 paths and compared to the pin (locate), then copied with that expected SHA.
7. **S1b admissions** have no prior expected SHA, because they are fresh copies. They are bound by the pinned r4 identities (E3) and, downstream, by S3 (the committed SHA must equal the S1b on-host SHA).
8. **Remote reader limitation (r3).** `remote_check` does not support E5 names. S10's reader requests never name a runtime member: P, F and POST name only directories.
